# CAD → SCADA / dashboard review

Inspection base: `7cff95e99c9584df09878793066f3c29fb45edfe` (2026-09-07).

## Existing flow

`CadController` exposes `/api/cad/convert` and `/api/cad/convert-per-entity`
for system/tenant administrators. `DefaultCadService` validates the upload,
creates a temporary conversion directory, executes `dwg_to_svg.py`, and returns
SVG resources / an entity manifest. DXF is parsed with ezdxf; DWG additionally
requires ODA File Converter. The legacy conversion route exports reusable block
symbols. The per-entity route drives the dashboard import dialog, selection,
deletions, individual/group widget mapping and SCADA-layout widget generation.

These are distinct outputs: an SVG symbol is reusable artwork with SCADA
metadata; an operational dashboard also needs ThingsBoard widget configuration,
entity aliases, telemetry keys, alarm/RPC bindings and a saved dashboard.
CAD geometry alone does not identify the correct live ThingsBoard device.

## Fixes in this PR

| Defect | Change / regression |
| --- | --- |
| Preview contains a separately rendered full drawing and transparent hitboxes; deleting a hitbox paints an opaque white bbox and hides retained crossing geometry. Returning to preview reconstructs the original drawing plus masks. | Build the editable preview from the exact entity SVG assets used for import. Each selectable group owns its real geometry. Remove groups rather than masking rectangles; rebuild from the manifest filtered by deleted IDs. Browser pixel comparison checks deletion and rebuild. |
| The composite resource uses the full drawing viewBox but its widget uses the union of remaining entities. Mapping/deleting an outer entity shrinks/moves the entire background. | Composite `previewX/Y/Width/Height` always equal the full frame. Keep one static background beneath individually mapped/grouped live widgets. |
| Concatenating independent SVG inner strings leaks repeated `.C1` styles and colliding defs IDs across entities; removing root SVGs can discard coordinate/namespace context. | Parse each generated SVG, inline its restricted class styles, namespace ID references, retain the root viewBox and position the nested viewport explicitly. The same builder feeds preview and export. |
| `atob()` returns bytes represented as a Latin-1 string, then subsequent UTF-8 encoding corrupts non-ASCII labels/metadata. | Explicit UTF-8 decoding/encoding, tested with Chinese and supplementary Unicode characters. |
| A malformed resource can silently turn into an empty SVG; preparation exceptions bypass import finalization. | Reject invalid resources and unsupported active/external SVG content before attachment; use a deferred observable and visible error path for synchronous preparation failures. |
| Duplicate/overlapping group membership can duplicate live widgets or silently drop members. | Deduplicate group members and reject conflicting groups instead of silently guessing. |

The shared builder deliberately accepts the static SVG subset generated by the
current converter. It is not a general arbitrary-SVG import facility. It rejects
foreign/active elements, event handlers, external references, dynamic CSS and
page-targeting selectors. Server-side SVG validation and resource quotas remain
necessary; client validation is not the security boundary.

**Compatibility:** the editable preview now shows the assets that will actually
be imported, rather than a separate higher-fidelity whole-document render.
This prevents misleading previews but does not repair the converter's existing
font/layer/INSERT fidelity limitations. A missing/invalid preview transform is
reported rather than guessing a WCS-to-SVG conversion. Existing generated
resources and already saved dashboards are not migrated or modified.

## Still open — do not interpret passing CAD CI as completion of these items

1. **Single canonical backend rendering.** The per-entity converter currently
   copies geometry into a temporary DXF context and renders the original document
   independently for its full preview. Layer/BYLAYER/BYBLOCK colors, linetypes,
   fonts, block transforms and attributes can diverge. Nested INSERT expansion
   has a depth limit. Render once with the original document context, retain
   top-level entity handles on actual drawing primitives and derive previews,
   individual symbols and filtered backgrounds from that scene. Use the actual
   renderer placement matrix; current manifest scale metadata uses a different
   coordinate-space constant from the full preview. Expose unsupported/hidden/
   failed entity counts instead of silently declaring full conversion success.
2. **Deployment and process isolation.** ODA currently has a hard-coded Windows
   executable path. Make the converter executable configurable, verify ODA
   argument ordering against the installed version and test real DWG samples on
   a suitably licensed runner. Bound input and output bytes, nested geometry,
   wall time, memory and per-tenant concurrency. Kill the whole subprocess tree
   on timeout/cancellation, not just its parent; avoid exposing stderr paths.
3. **Non-destructive editing and auditability.** Deletion currently means
   exclusion from this import, NOT rewriting the uploaded DWG/DXF. Persist source
   hash, schema version, stable entity handles/instance paths, edit operations
   and mapping revision. Add undo/redo and layer/block/type filters with a
   confirmed match count. A cleaned DXF/DWG download is a separate backend export
   feature and must preserve blocks/references; it is not implemented here.
4. **Device binding and import transactions.** Current mapped widgets start from
   widget-type defaults with empty datasources. Add explicit rules such as
   block name + equipment-tag attribute → widget type + entity alias + telemetry
   keys. Preview ambiguous matches; never guess RPC targets. Cache repeated
   widget-type lookups. Persist/import resources transactionally or track and
   clean up resources on cancellation/failure. Existing partial-upload behavior
   closes the dialog after setting a message, so a durable result report/retry
   design remains necessary.
5. **Full-system validation.** Add representative, authorized real drawings:
   rotated/mirrored/nested blocks, Chinese fonts, hatch/spline/dimension geometry,
   layouts, invisible layers, extreme coordinates, and malformed input. Compare
   against an agreed CAD reference render. Add a deployed ThingsBoard browser
   test for upload → edit → device binding → save → reload, and tenant/security
   tests for the Java service. This PR's fast CI is not that full-system test.

## Recommended target design

```text
Original DWG/DXF (immutable, tenant-scoped, content hash)
  → isolated conversion job / progress / cancellation
  → canonical CadDocument (stable IDs, hierarchy, layers, attributes,
      WCS bounds, one modelToSvg matrix, one viewBox, render primitives)
  → non-destructive edits (deleted IDs, grouping, mapping rules)
  ├─ symbol export → reusable SCADA SVG + metadata
  ├─ dashboard projection → one static background + N live widgets
  └─ optional cleaned-CAD export (separate verified writer)
```

This keeps drawing complexity out of the live widget count: hundreds of static
pipes/text strokes should not create hundreds of Angular widgets. Only equipment
that needs live telemetry, alarms or interaction becomes a live widget. SCADA
and ordinary dashboard views should be projections of the same document and
binding model, not independent parsers.

## Validation

`.github/workflows/cad-import-regression.yml` runs on relevant PRs, master pushes
and manual dispatch. It uses read-only repository permissions and does not
install the full ThingsBoard UI dependency graph:

- The existing Python converter tests (no production tests removed).
- Every standalone `cad*.spec.ts` under the CAD dialog, discovered automatically.
- Strict TypeScript compilation of the production scene/import-planner helpers.
- Real Chromium rendering, hit-testing, UTF-8, ID/style isolation, negative SVG
  validation, deletion/rebuild, full-frame layout and bulk static-widget tests.
- A real DXF → current Python converter → browser preview → filtered background
  contract test. Its before/export PNGs and JUnit results are uploaded as artifacts.

For local browser helper tests install the workflow's pinned Python/Node test
tools, place `tsc` on PATH, then run:

```sh
python -m playwright install chromium
python -m pytest -q tests/cad
```

To use a system Chromium, set `CAD_CHROMIUM_EXECUTABLE=/path/to/chromium`.
Full Angular template/build verification, Java integration tests, proprietary
ODA/DWG execution and production device connections are explicitly outside the
fast suite; do not claim they passed based on this workflow alone.
